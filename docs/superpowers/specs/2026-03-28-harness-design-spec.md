# Harness Design Implementation Spec

Date: 2026-03-28
Status: Approved (pending implementation)
Reviewed by: Codex (2 rounds)

## Summary

Claude Code Starter Kit にハーネスエンジニアリングパターンを導入する。
Anthropic 公式記事の3エージェント構成（Planner→Generator→Evaluator）、
スプリント契約、多層フィードバックループの原則に基づく。

### Success Criteria

- [ ] 厳格な Evaluator（qa-reviewer）が evidence-based で合否判定できる
- [ ] /orchestrate が Planner→Generator→Evaluator の repair loop を持つ
- [ ] /init-harness がプロジェクト固有フックを冪等に生成できる
- [ ] 技術スタック固有フック（prettier, console-log-guard）がグローバルから除去されている
- [ ] pre-commit-gate が advisory モードで動作する
- [ ] post-test-analysis が失敗時のみ発火する
- [ ] 全フックの成功パス出力が 0 トークン、失敗パスが 30 トークン以下

### Out of Scope

- Playwright MCP 連携（E2E 自動実行）
- エスカレーションラダー（違反回数の自動追跡）
- Generator 専用エージェント（既存の tdd-guide を Generator ロールとして使用）

### 設計原則

| 原則 | 適用 |
|------|------|
| 生成と評価の分離 | qa-reviewer は evidence のみ入力、ソース直接閲覧禁止 |
| グローバル = 汎用、プロジェクト = 固有 | lint/format/type フックはプロジェクトレベルに移動 |
| 成功パスはサイレント | 全フック出力 0 トークン（成功時） |
| 冪等性 | /init-harness は何度実行しても同じ結果 |
| Advisory デフォルト | ブロック動作は明示的な opt-in のみ |

## Design

### Component Overview

```
[Layer 1: Global (~/.claude/)]
  agents/qa-reviewer.md .............. G1: 厳格な評価器
  commands/orchestrate.md ............ G1b: Generator + repair loop 追加
  features/harness-init/ ............. G2: SessionStart 検出 + 提案

[Layer 2: Project (.claude/) — generated by /init-harness]
  .claude/settings.json .............. スタック固有フック（lint, format, type）

[Deleted]

  features/console-log-guard/ ........ → /init-harness JS/TS テンプレートに移行
```

### G1: qa-reviewer Agent

**File**: `agents/qa-reviewer.md`

**Role**: Sprint contract の検証基準に対して evidence-based で Pass/Fail を判定する厳格な評価器。

**Input contract (HARD SCOPE)**:
- Evidence bundle のみ（テスト結果、ビルドログ、lint 出力、変更 diff）
- ソースコードの直接閲覧は禁止
- Sprint contract（検証基準リスト）が必須入力

**Output format**:
```markdown
## QA Evaluation Report

### Sprint Contract: [task name]
| # | Criterion | Verdict | Evidence |
|---|-----------|---------|----------|
| 1 | User registration works | PASS | test/auth.test.ts all passed |
| 2 | Validation error displayed | FAIL | Empty input returns 500 (expected: 422) |
| 3 | tsc --noEmit clean | PASS | exit code 0 |

### Overall: FAIL (1/3 failed)
### Repair Instructions: [specific fix steps]
```

**Behavioral rules**:
- "Looks good" / "generally fine" / "minor issue" judgments are PROHIBITED
- Every criterion must have PASS or FAIL with concrete evidence
- FAIL triggers repair instructions with specific file paths and expected behavior

**Size constraint**: ~600-800 tokens (matching code-reviewer.md)

**Differentiation from code-reviewer**:

| Aspect | code-reviewer | qa-reviewer |
|--------|---------------|-------------|
| Input | Source code (git diff) | Evidence bundle only |
| Judgment | Quality suggestions | Pass/Fail grading |
| Criteria | Generic checklist | Sprint contract (per-task) |
| Output | Improvement comments | Grading report + repair instructions |
| Invocation | After any code change | After implementation sprint in /orchestrate |

### G1b: /orchestrate Generator Stage

**File**: `commands/orchestrate.md` (modify existing)

**Modified `feature` workflow**:

```
Phase 1: Planning
  planner → produces implementation plan + sprint contract
  Sprint contract = list of testable acceptance criteria

Phase 2: Generation (NEW)
  Generator (tdd-guide) receives:
    - Implementation plan
    - Sprint contract (acceptance criteria)
  Generator produces:
    - Implementation code
    - Test results
    - Build/lint output
    - Evidence bundle file

Phase 3: Evaluation (NEW)
  qa-reviewer receives:
    - Sprint contract
    - Evidence bundle (test results + build logs + lint + diff)
  qa-reviewer produces:
    - Grading report (Pass/Fail per criterion)

  If FAIL:
    → Repair instructions sent back to Generator
    → Generator re-implements
    → qa-reviewer re-evaluates
    → Max 3 iterations, then escalate to user

Phase 4: Review (existing, after qa-reviewer PASS)
  Parallel:
    - code-reviewer (quality)
    - security-reviewer (security)
```

**Handoff artifact format** (planner → generator):
```markdown
## Implementation Contract

### Task: [description]

### Acceptance Criteria (Sprint Contract)
1. [Testable criterion with expected behavior]
2. [Testable criterion with expected behavior]
3. ...

### Technical Constraints
- [Stack, patterns, dependencies]

### Files to Modify
- [file paths]
```

**Evidence bundle format** (generator → qa-reviewer):
```markdown
## Evidence Bundle

### Test Results
[stdout/stderr of test command, exit code]

### Build Results
[stdout/stderr of build command, exit code]

### Lint Results
[stdout/stderr of lint command, exit code]

### Changed Files
[git diff --stat output]
```

### G2: harness-init Feature

**Files**:
- `features/harness-init/feature.json`
- `features/harness-init/hooks.json`
- `features/harness-init/scripts/detect-stack.sh`

**feature.json**:
```json
{
  "name": "harness-init",
  "displayName": "Harness Init Detection",
  "description": "Detects project tech stack and suggests /init-harness setup",
  "category": "harness",
  "default": true,
  "dependencies": [],
  "conflicts": []
}
```

**hooks.json**:
```json
{
  "hooks": {
    "SessionStart": [{
      "matcher": "*",
      "hooks": [{
        "type": "command",
        "command": "__HOME__/.claude/hooks/harness-init/detect-stack.sh"
      }]
    }]
  }
}
```

**detect-stack.sh behavior**:
```
1. Get project root (git rev-parse --show-toplevel || pwd)
2. Compute repo identity hash (based on absolute path)
3. Check ~/.claude/.harness-init-suggested for this hash
   → If already suggested: exit 0 (silent)
4. Check if .claude/settings.json exists with hooks entries
   → If hooks exist: record hash + exit 0 (silent)
5. Detect tech stack:
   - package.json + tsconfig.json → "typescript"
   - package.json (no tsconfig) → "javascript"
   - composer.json → "php"
   - Package.swift → "swift"
   - build.gradle or build.gradle.kts → "kotlin"
   - Makefile → "generic"
   - None matched → exit 0 (silent)
6. Record hash in ~/.claude/.harness-init-suggested
7. Output to stdout (~20 tokens):
   "[harness] <Stack> project detected. Run /init-harness to set up verification hooks."
```

**Token budget**: 0 tokens (already suggested or hooks exist) / ~20 tokens (first suggestion)

### G2b: /init-harness Command

**Files**:
- `commands/init-harness.md`
- `commands/templates/typescript.json`
- `commands/templates/javascript.json`
- `commands/templates/php.json`
- `commands/templates/swift.json`
- `commands/templates/kotlin.json`
- `commands/templates/generic.json`

**init-harness.md** defines a Claude slash command (markdown instruction file, not a shell script).
Claude reads the instruction and executes the steps using its tools (Bash with jq, Read, Write).

1. Detects the project tech stack (same logic as detect-stack.sh)
2. Reads the appropriate template from `commands/templates/`
3. If `.claude/settings.json` exists:
   - Performs **idempotent merge**:
     - Objects: deep merge (preserve existing keys)
     - Hook arrays: dedupe by `(event type, matcher, command)` tuple
     - If an entry with the same identity exists: replace it
     - If new: append it
   - Shows unified diff of proposed changes
   - Asks user for confirmation
4. If `.claude/settings.json` does not exist:
   - Generates from template
   - Shows generated content
   - Asks user for confirmation
5. Writes file only after user approval

**Template example (typescript.json)**:
```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "tool == \"Edit\" && file_path =~ \"\\.(ts|tsx|js|jsx)$\"",
        "hooks": [{
          "type": "command",
          "command": "npx prettier --write \"$CLAUDE_FILE_PATH\" 2>/dev/null; exit 0"
        }]
      },
      {
        "matcher": "tool == \"Edit\" && file_path =~ \"\\.(ts|tsx|js|jsx)$\"",
        "hooks": [{
          "type": "command",
          "command": "grep -n 'console\\.log' \"$CLAUDE_FILE_PATH\" && echo '[warn] console.log detected' >&2; exit 0"
        }]
      }
    ],
    "PreToolUse": [
      {
        "matcher": "tool == \"Bash\" && command =~ \"git commit\"",
        "hooks": [{
          "type": "command",
          "command": "npx tsc --noEmit 2>&1 | tail -5; exit 0"
        }]
      }
    ]
  }
}
```

**Idempotent merge strategy**:

Hook entry identity = `(hook_type, matcher, command_prefix)` where `command_prefix` is the first 50 characters of the command string. This allows:
- Re-running `/init-harness` safely (updates existing entries, no duplicates)
- Preserving user-added hooks (different identity = kept)
- Updating kit-managed hooks (same identity = replaced)

### G3: pre-commit-gate Feature

**Files**:
- `features/pre-commit-gate/feature.json`
- `features/pre-commit-gate/hooks.json`
- `features/pre-commit-gate/scripts/pre-commit-gate.sh`

**feature.json**:
```json
{
  "name": "pre-commit-gate",
  "displayName": "Pre-Commit Verification Gate",
  "description": "Runs verification before git commit (advisory by default)",
  "category": "harness",
  "default": true,
  "dependencies": [],
  "conflicts": []
}
```

**hooks.json**:
```json
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "tool == \"Bash\" && command =~ \"git commit\"",
      "hooks": [{
        "type": "command",
        "command": "__HOME__/.claude/hooks/pre-commit-gate/pre-commit-gate.sh"
      }]
    }]
  }
}
```

**pre-commit-gate.sh behavior**:
```
1. Read tool event from stdin
2. Determine verification commands:
   Priority: env vars > auto-detect > skip

   env vars checked:
     VERIFY_TEST → test command
     VERIFY_LINT → lint command
     VERIFY_TYPE → type check command

   Auto-detect (if no env vars):
     package.json + scripts.test → npm test
     Makefile + test target → make test
     composer.json + scripts.test → composer test

   Extended runner detection (Codex feedback):
     pnpm exec vitest, npm run test:*, just test, make ci-test

   Nothing found → exit 0 (silent pass-through)

3. Run detected commands
4. Check results:
   HARNESS_GATE_MODE == "strict":
     → Failure: exit 1 (blocks commit)
     → Success: exit 0 (silent, 0 tokens)
   HARNESS_GATE_MODE unset (default advisory):
     → Failure: exit 0 + stderr warning (~20 tokens)
       "⚠ Verification failed. Commit proceeds (advisory mode)."
     → Success: exit 0 (silent, 0 tokens)
```

**Token budget**: 0 tokens (success or no commands) / ~20 tokens (advisory failure)

### G5: post-test-analysis Feature

**Files**:
- `features/post-test-analysis/feature.json`
- `features/post-test-analysis/hooks.json`
- `features/post-test-analysis/scripts/analyze-test.sh`

**feature.json**:
```json
{
  "name": "post-test-analysis",
  "displayName": "Post-Test Failure Analysis",
  "description": "Analyzes test failures and outputs summary (failure-only)",
  "category": "harness",
  "default": true,
  "dependencies": [],
  "conflicts": []
}
```

**hooks.json**:
```json
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "tool == \"Bash\" && exit_code != 0",
      "hooks": [{
        "type": "command",
        "command": "__HOME__/.claude/hooks/post-test-analysis/analyze-test.sh",
        "timeout": 5000
      }]
    }]
  }
}
```

**analyze-test.sh behavior**:
```
1. Read tool event from stdin
2. Extract command and exit_code
3. exit_code == 0 → exit 0 (impossible due to matcher, but safety check)
4. Check if command matches test runner pattern:
   Patterns (extended per Codex feedback):
     npm test, npx jest, npx vitest, npx mocha,
     pnpm exec vitest, pnpm test, yarn test,
     npm run test:*, jest, vitest,
     pytest, python -m pytest,
     swift test, xcodebuild test,
     ./gradlew test, gradle test,
     make test, make ci-test, just test,
     cargo test, go test

   No match → exit 0 (silent, not a test command)

5. Extract failure summary from tool_response.stdout:
   - Count of failed tests (regex: /(\d+) failed/, /FAILED.*(\d+)/, etc.)
   - Up to 3 failed test names (regex: /FAIL.*?(\S+)/, etc.)

6. Output to stdout (~30 tokens max):
   "[test] N tests failed: name1, name2, name3. Check output above."
```

**Token budget**: 0 tokens (success or non-test command) / ~30 tokens (test failure)

## Context Window Budget

| Injection Point | Tokens/trigger | Frequency | Session Total |
|-----------------|---------------|-----------|---------------|
| harness-init SessionStart | 0 or ~20 | Once ever per repo | 0-20 |
| pre-commit-gate (success) | 0 | Per commit | 0 |
| pre-commit-gate (fail, advisory) | ~20 | 0-2x/session | 0-40 |
| post-test-analysis (success) | 0 | N/A (not triggered) | 0 |
| post-test-analysis (fail) | ~30 | 0-5x/session | 0-150 |
| qa-reviewer.md load | ~700 | On invocation only | 0-700 |
| **Total new budget** | | | **0-910** |

Baseline: existing hooks inject ~2000-5000 tokens/session.
New additions: worst case +910, typical case +50-70.
**Codex verdict: acceptable.**

## Risks and Mitigations

| Risk | Mitigation |
|------|-----------|
| /init-harness duplicates hooks on rerun | Idempotent merge with (type, matcher, command_prefix) identity |
| qa-reviewer drifts into code review | Hard-scoped: evidence bundle only, no source file access, enforced in /orchestrate |
| pre-commit-gate blocks legitimate commits | Advisory default, strict only via explicit HARNESS_GATE_MODE=strict |
| post-test-analysis too noisy | Failure-only trigger, ~30 tokens max |
| Test runner detection misses wrapper commands | Extended pattern list including pnpm exec, npm run test:*, just, make ci-test |
| Existing users lose prettier/console-log-guard | Migration message + /init-harness provides equivalent project-level hooks |
