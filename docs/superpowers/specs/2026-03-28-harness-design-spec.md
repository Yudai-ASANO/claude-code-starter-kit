# Harness Design Implementation Spec

Date: 2026-03-28
Status: APPROVED (v5.1) — Codex round 6: APPROVE WITH CONDITIONS (condition resolved)
Reviewed by: Codex (6 rounds)

## Summary

Claude Code Starter Kit にハーネスエンジニアリングパターンを導入する。
Anthropic 公式記事の3エージェント構成（Planner→Generator→Evaluator）、
スプリント契約、多層フィードバックループの原則に基づく。

### Success Criteria

- [ ] 厳格な Evaluator（qa-reviewer）がオーケストレーター収集の evidence で合否判定できる
- [ ] /orchestrate が Planner→Generator→Evaluator の repair loop を持つ
- [ ] Sprint contract に executable verifier が含まれる
- [ ] /init-harness がプロジェクト固有フックをマニフェストベースで冪等に生成できる
- [ ] 技術スタック固有フック（prettier, console-log-guard）がグローバルから除去されている
- [ ] pre-commit-gate が advisory モードで動作する
- [ ] 全フックの成功パス出力が 0 トークン

### Out of Scope

- Playwright MCP 連携（E2E 自動実行）
- エスカレーションラダー（違反回数の自動追跡）
- Generator 専用エージェント（既存の tdd-guide を Generator ロールとして使用）

### 設計原則

| 原則 | 適用 |
|------|------|
| 生成と評価の分離 | オーケストレーターが evidence を収集。Evaluator は Generator 作成物を直接読まない |
| グローバル = 汎用、プロジェクト = 固有 | lint/format/type フックはプロジェクトレベルに移動 |
| 成功パスはサイレント | 全フック出力 0 トークン（成功時） |
| 冪等性 | /init-harness はマニフェストベースで重複を防止 |
| Advisory デフォルト | ブロック動作は明示的な opt-in のみ |
| Executable contract | Sprint contract の各基準に verifier コマンドと期待結果を含む |

### Codex REJECT 修正履歴

**Round 2 → v2 修正:**

| Codex 指摘 | 修正内容 |
|---|---|
| C1: Evaluator の独立性不完全 | オーケストレーターが evidence を収集する設計に変更。evidence bundle から diff を除外 |
| C2: hook schema が既存と不一致 | 全テンプレート・マッチャーを `tool_input.*` / `tool_output.*` 形式に統一 |
| W1: Sprint contract が曖昧 | eval-harness の code-grader パターンを借用。各基準に verifier + expected + location を追加 |
| W2: 冪等マージの identity が矛盾 | prefix マッチ廃止。`.claude/.harness-manifest.json` による明示的マニフェスト管理に変更 |
| W3: コンテキスト予算が過小評価 | post-test-analysis をデフォルト OFF（opt-in）に変更。console-log-guard をデフォルト生成しない |

**Round 3 → v3 修正:**

| Codex 指摘 | 修正内容 |
|---|---|
| C1: post-test-analysis が stdout に人間向けテキストを出力（パススルーパターン違反） | 人間向け出力を stderr のみに変更。stdout はパススルー JSON のみ。全フックに OUTPUT DISCIPLINE ルールを明記 |
| C2: pre-commit-gate の verifier 出力が無制限でトークン予算不正確 | verifier 出力を `tail -5` で truncate しテンプファイルに保存。stdout/stderr に漏出させない。1行サマリーのみ stderr に出力 |
| W1: マニフェスト tombstone に回復パスがない | `/init-harness --reset`（マニフェスト削除 + 再構築）と `--reinstall-managed`（tombstone クリアのみ）を追加 |

**Round 4 → v4 修正:**

| Codex 指摘 | 修正内容 |
|---|---|
| C1: pre-commit-gate の exit code がパイプラインで失われる | パイプライン廃止。`cmd > tmpfile 2>&1; exit=$?` で直接キャプチャに変更 |
| W1: コンテキスト予算表が stderr と stdout を混同 | 予算表を stdout-only モデルに統一。stderr は context 外として明記 |

**Round 5 → v5 修正:**

| Codex 指摘 | 修正内容 |
|---|---|
| C1: set -e 下で verifier 失敗時にスクリプトが即終了する | `if cmd > tmp 2>&1; then exit=0; else exit=$?; fi` パターンに変更 |
| W1: シナリオ表の「Combined with existing」が baseline ~0-85 と不整合 | シナリオ表を baseline と一貫した stdout-only 数値に修正 |

### G1: qa-reviewer Agent

**File**: `agents/qa-reviewer.md`

**Role**: Sprint contract の executable verifier 結果に基づいて Pass/Fail を判定する厳格な評価器。

**Input contract (HARD SCOPE)**:
- **オーケストレーター収集の evidence のみ**（Generator が作成した bundle は使わない）
- evidence 内容: verifier コマンド実行結果（stdout/stderr + exit code）、ビルドログ、lint 出力
- **diff は含めない**（diff を読むとソースレビューと同義になるため）
- Sprint contract（executable verifier 付き検証基準リスト）が必須入力

**Output format**:
```markdown
## QA Evaluation Report

### Sprint Contract: [task name]
| # | Criterion | Verifier | Expected | Actual | Verdict |
|---|-----------|----------|----------|--------|---------|
| 1 | User registration works | npm test -- --grep "register" | exit 0 | exit 0 | PASS |
| 2 | Validation returns 422 | curl -s -o /dev/null -w "%{http_code}" localhost:3000/api/register | 422 | 500 | FAIL |
| 3 | tsc clean | npx tsc --noEmit | exit 0 | exit 0 | PASS |

### Overall: FAIL (1/3 failed)
### Repair Instructions:
- Criterion 2: POST /api/register with empty body returns 500.
  Expected 422 with validation error. Check request validation middleware.
```

**Behavioral rules**:
- "Looks good" / "generally fine" / "minor issue" judgments are PROHIBITED
- Every criterion must have PASS or FAIL based on verifier output comparison
- FAIL triggers repair instructions scoped to the failing criterion and subsystem (not guessed file paths)
- Repair instructions reference failing verifier output, not source code

**Size constraint**: ~600-800 tokens (matching code-reviewer.md at ~105 lines)

**Differentiation from code-reviewer**:

| Aspect | code-reviewer | qa-reviewer |
|--------|---------------|-------------|
| Input | Source code (git diff) | Verifier results only (no diff) |
| Judgment | Quality suggestions | Pass/Fail per criterion |
| Criteria | Generic checklist | Executable sprint contract |
| Evidence | Code inspection | Command output comparison |
| Output | Improvement comments | Grading report + criterion-scoped repair |
| Invocation | After any code change | After implementation sprint in /orchestrate |

### G1b: /orchestrate Generator Stage

**File**: `commands/orchestrate.md` (modify existing)

**Modified `feature` workflow**:

```
Phase 1: Planning
  planner → produces implementation plan + executable sprint contract
  Sprint contract = list of criteria with verifier commands

Phase 2: Generation
  Generator (tdd-guide) receives:
    - Implementation plan
    - Sprint contract
  Generator produces:
    - Implementation code
    - (Generator does NOT produce the evidence bundle)

Phase 3: Evidence Collection (NEW — orchestrator responsibility)
  The orchestrator (Claude main) collects evidence by running:
    - Each verifier command from the sprint contract
    - Build command (if applicable)
    - Lint command (if applicable)
  Evidence is raw command output, not filtered by Generator.

Phase 4: Evaluation
  qa-reviewer receives:
    - Sprint contract (with verifier definitions)
    - Orchestrator-collected evidence (verifier outputs)
  qa-reviewer produces:
    - Grading report (Pass/Fail per criterion)

  If FAIL:
    → Repair instructions (criterion-scoped) sent back to Generator
    → Generator re-implements
    → Orchestrator re-collects evidence
    → qa-reviewer re-evaluates
    → Max 3 iterations, then escalate to user

Phase 5: Review (after qa-reviewer PASS)
  Parallel:
    - code-reviewer (quality)
    - security-reviewer (security)
```

**Executable sprint contract format** (planner → orchestrator):
```markdown
## Sprint Contract

### Task: [description]

### Acceptance Criteria
| # | Criterion | Verifier Command | Expected Result |
|---|-----------|-----------------|-----------------|
| 1 | User can register | npm test -- --grep "register" | exit 0 |
| 2 | Invalid input returns 422 | curl -s -o /dev/null -w "%{http_code}" localhost:3000/api/register -d '{}' | stdout: "422" |
| 3 | TypeScript compiles | npx tsc --noEmit | exit 0 |
| 4 | No lint errors | npx eslint src/ | exit 0 |

### Technical Constraints
- [Stack, patterns, dependencies]

### Files to Modify
- [file paths]
```

**Evidence collection format** (orchestrator → qa-reviewer):
```markdown
## Evidence (collected by orchestrator)

### Criterion 1: User can register
Command: npm test -- --grep "register"
Exit code: 0
Stdout: [truncated to last 20 lines]

### Criterion 2: Invalid input returns 422
Command: curl -s -o /dev/null -w "%{http_code}" localhost:3000/api/register -d '{}'
Exit code: 0
Stdout: 500

### Criterion 3: TypeScript compiles
Command: npx tsc --noEmit
Exit code: 0
Stdout: (empty)

### Criterion 4: No lint errors
Command: npx eslint src/
Exit code: 0
Stdout: (empty)
```

### G2: harness-init Feature

**Files**:
- `features/harness-init/feature.json`
- `features/harness-init/hooks.json`
- `features/harness-init/scripts/detect-stack.sh`

**feature.json**:
```json
{
  "name": "harness-init",
  "displayName": "Harness Init Detection",
  "description": "Detects project tech stack and suggests /init-harness setup",
  "category": "harness",
  "default": true,
  "dependencies": [],
  "conflicts": []
}
```

**hooks.json**:
```json
{
  "hooks": {
    "SessionStart": [{
      "matcher": "*",
      "hooks": [{
        "type": "command",
        "command": "__HOME__/.claude/hooks/harness-init/detect-stack.sh"
      }]
    }]
  }
}
```

**detect-stack.sh behavior**:
```
1. Get project root: git rev-parse --show-toplevel 2>/dev/null || pwd
2. Compute repo identity hash: printf '%s' "$project_root" | shasum | cut -d' ' -f1
3. Check ~/.claude/.harness-init-suggested for this hash
   → If already suggested: exit 0 (silent, 0 tokens)
4. Check if .claude/settings.json exists AND contains "hooks" key with entries
   → If hooks exist: record hash + exit 0 (silent, 0 tokens)
5. Detect tech stack:
   - package.json + tsconfig.json → "TypeScript"
   - package.json (no tsconfig) → "JavaScript"
   - composer.json → "PHP"
   - Package.swift → "Swift"
   - build.gradle or build.gradle.kts → "Kotlin"
   - Cargo.toml → "Rust"
   - go.mod → "Go"
   - Makefile → "Generic"
   - None matched → exit 0 (silent, 0 tokens)
6. Record hash in ~/.claude/.harness-init-suggested
7. Output to stdout (~15 tokens):
   "[harness] <Stack> project detected. Run /init-harness to set up verification hooks."
```

**Token budget**: 0 (repeat visit or hooks exist) / ~15 (first-ever suggestion for this repo)

### G2b: /init-harness Command

**Files**:
- `commands/init-harness.md`
- `commands/templates/typescript.json`
- `commands/templates/javascript.json`
- `commands/templates/php.json`
- `commands/templates/swift.json`
- `commands/templates/kotlin.json`
- `commands/templates/generic.json`

**init-harness.md** defines a Claude slash command (markdown instruction file).
Claude reads the instruction and executes the steps using its tools (Bash with jq, Read, Write).

1. Detects the project tech stack (same logic as detect-stack.sh)
2. Reads the appropriate template from `commands/templates/`
3. **Manifest-based idempotent merge**:
   a. Read or create `.claude/.harness-manifest.json`:
      ```json
      {
        "managed_hooks": [
          {
            "id": "harness:typescript:prettier",
            "hook_type": "PostToolUse",
            "matcher": "tool == 'Edit' && tool_input.file_path matches '\\.(ts|tsx|js|jsx)$'",
            "command_hash": "a1b2c3d4..."
          }
        ],
        "stack": "typescript",
        "version": "0.36.0"
      }
      ```
   b. For each hook in the template:
      - Compute `command_hash` (SHA-256 of full command string)
      - If `id` exists in manifest AND in settings.json: **replace** (update)
      - If `id` exists in manifest but NOT in settings.json: user deleted it → **skip**
        (tombstone: user intentionally removed this hook)
      - If `id` not in manifest: **append** (new hook)
   c. Hooks NOT in manifest (user-added): **preserve untouched**
   d. Update `.claude/.harness-manifest.json`
4. Shows unified diff of proposed changes
5. Asks user for confirmation before writing

**Recovery modes**:
- `/init-harness --reset`: Deletes `.claude/.harness-manifest.json` and re-runs from scratch.
  This clears all tombstones and re-installs all managed hooks as if first run.
- `/init-harness --reinstall-managed`: Re-installs only previously managed hooks that were
  removed (clears tombstones), without affecting user-added hooks or current managed hooks.

**Template example (typescript.json)** — using correct hook schema:
```json
{
  "hooks": {
    "PostToolUse": [
      {
        "_id": "harness:typescript:prettier",
        "matcher": "tool == 'Edit' && tool_input.file_path matches '\\.(ts|tsx|js|jsx)$'",
        "hooks": [{
          "type": "command",
          "command": "#!/bin/bash\ninput=$(cat)\nfile_path=$(printf '%s' \"$input\" | jq -r '.tool_input.file_path // \"\"')\nif [ -n \"$file_path\" ] && [ -f \"$file_path\" ]; then\n  npx prettier --write \"$file_path\" 2>/dev/null\nfi\nprintf '%s\\n' \"$input\""
        }]
      },
      {
        "_id": "harness:typescript:tsc-check",
        "matcher": "tool == 'Edit' && tool_input.file_path matches '\\.(ts|tsx)$'",
        "hooks": [{
          "type": "command",
          "command": "#!/bin/bash\ninput=$(cat)\nnpx tsc --noEmit 2>&1 | tail -3 >&2\nprintf '%s\\n' \"$input\""
        }]
      }
    ]
  }
}
```

Note: `_id` field is used by `/init-harness` for manifest tracking. Claude Code ignores unknown fields in hook entries. The `_id` is also recorded in `.harness-manifest.json` for idempotent updates.

**console-log-guard is NOT included by default** (Codex W3). Users can add it manually or request it via `/init-harness --with-console-guard`.

### G3: pre-commit-gate Feature

**Files**:
- `features/pre-commit-gate/feature.json`
- `features/pre-commit-gate/hooks.json`
- `features/pre-commit-gate/scripts/pre-commit-gate.sh`

**feature.json**:
```json
{
  "name": "pre-commit-gate",
  "displayName": "Pre-Commit Verification Gate",
  "description": "Runs verification before git commit (advisory by default)",
  "category": "harness",
  "default": true,
  "dependencies": [],
  "conflicts": []
}
```

**hooks.json** — using correct hook schema:
```json
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "tool == \"Bash\" && tool_input.command matches \"git commit\"",
      "hooks": [{
        "type": "command",
        "command": "__HOME__/.claude/hooks/pre-commit-gate/pre-commit-gate.sh"
      }]
    }]
  }
}
```

**pre-commit-gate.sh behavior**:
```
1. Read tool event from stdin
2. Determine verification commands:
   Priority: env vars > auto-detect > skip

   env vars checked (from settings.json env or project .claude/settings.json env):
     VERIFY_TEST → test command
     VERIFY_LINT → lint command
     VERIFY_TYPE → type check command

   Auto-detect (if no env vars):
     package.json with scripts.test → npm test
     package.json with scripts.lint → npm run lint
     Makefile with test: target → make test
     composer.json with scripts.test → composer test
     Cargo.toml → cargo test
     go.mod → go test ./...

   Extended detection:
     pnpm-lock.yaml → pnpm test instead of npm test
     yarn.lock → yarn test instead of npm test
     Justfile with test recipe → just test

   Nothing found → pass through input on stdout, exit 0 (silent, 0 tokens)

3. Run detected commands with EXPLICIT OUTPUT BOUNDING and EXIT CODE PRESERVATION:
   For each verifier (safe under set -euo pipefail):
     if cmd > /tmp/.gate-out-$$ 2>&1; then
       verifier_exit=0
     else
       verifier_exit=$?
     fi
   The if/else prevents set -e from aborting the script on verifier failure.
   No pipelines are used — command writes directly to a temp file.
   Output is truncated to last 5 lines only when building the summary.
   Temp files are cleaned up via trap EXIT.

4. Check results:
   HARNESS_GATE_MODE == "strict" (explicit opt-in):
     → Failure: exit 1 (blocks commit). stderr: 1-line summary only.
     → Success: pass through input on stdout, exit 0 (silent, 0 tokens)
   HARNESS_GATE_MODE unset (default advisory):
     → Failure: 1-line summary to stderr (~20 tokens), pass through input on stdout, exit 0
       stderr: "[gate] Verification failed: test(1) lint(0). Advisory mode — commit proceeds."
     → Success: pass through input on stdout, exit 0 (silent, 0 tokens)

   OUTPUT DISCIPLINE:
   - stdout: ONLY the pass-through JSON input (never human text)
   - stderr: ONLY 1-line summary on failure (never raw verifier output)
   - Raw verifier output stays in temp file (cleaned up on exit)
```

**Token budget**: 0 (success or no commands) / ~20 stderr only on advisory failure (bounded)

### G5: post-test-analysis Feature

**CHANGED: default OFF (opt-in only)** per Codex W3.

**Files**:
- `features/post-test-analysis/feature.json`
- `features/post-test-analysis/hooks.json`
- `features/post-test-analysis/scripts/analyze-test.sh`

**feature.json**:
```json
{
  "name": "post-test-analysis",
  "displayName": "Post-Test Failure Analysis",
  "description": "Analyzes test failures and outputs summary (opt-in, failure-only)",
  "category": "harness",
  "default": false,
  "dependencies": [],
  "conflicts": []
}
```

**hooks.json** — using correct hook schema:
```json
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "tool == 'Bash' && tool_output.exit_code != null && tool_output.exit_code != 0",
      "hooks": [{
        "type": "command",
        "command": "__HOME__/.claude/hooks/post-test-analysis/analyze-test.sh",
        "timeout": 5000
      }]
    }]
  }
}
```

**analyze-test.sh behavior**:
```
1. Read tool event from stdin
2. Extract command: jq -r '.tool_input.command // ""'
3. Check if command matches test runner pattern:
   Patterns:
     npm test, npx (jest|vitest|mocha),
     pnpm (test|exec vitest), yarn test,
     npm run test:*,
     pytest, python -m pytest,
     swift test, xcodebuild test,
     ./gradlew test, gradle test,
     make test, make ci-test, just test,
     cargo test, go test

   No match → pass through input on stdout, exit 0 (silent, 0 tokens)

4. Extract failure summary from tool_output:
   - Count of failed tests (regex patterns for each runner)
   - Up to 3 failed test names

5. OUTPUT DISCIPLINE:
   - stdout: ONLY the pass-through JSON input (never human text)
   - stderr: 1-line failure summary (~25 tokens max):
     "[test] N failed: name1, name2, name3."
   This matches the repo convention: human text → stderr, JSON pass-through → stdout.
   (See: prettier-hooks, doc-blocker, check-codex-before-write)
```

**Token budget**: 0 (not enabled by default) / ~25 per test failure (when opt-in enabled)

## Context Window Budget (Revised)

### Context model

**"Context tokens" = stdout-only.** Claude Code injects hook stdout into the conversation context.
Hook stderr is displayed to the user's terminal but does NOT enter Claude's context window.
All token counts below refer to stdout output only.

### Existing hooks baseline (standard profile, all defaults ON, stdout-only)

| Hook Type | Existing Hooks | stdout context tokens/session |
|---|---|---|
| SessionStart | auto-update (0 normally), memory-persistence (~0-45 stdout) | ~0-45 |
| PreToolUse | safety-net (0, stderr only), strategic-compact (0 stdout, stderr only), git-push-review (0, stderr only), doc-blocker (0, stderr + exit 1) | 0 |
| PostToolUse | pr-creation-log (0, stderr only), check-codex-before-write (0, stderr only), check-codex-after-plan (0, stderr only), error-to-codex (0, stderr only) | 0 |
| PreCompact | memory-persistence (~0-20 stdout), pre-compact-commit (~0) | ~0-20 |
| Stop | memory-persistence (~0-20 stdout) | ~0-20 |
| **Existing total (stdout context)** | | **~0-85** |

Note: Existing hooks that appear "noisy" (check-codex-before-write, error-to-codex, etc.)
actually write only to stderr. Their context impact is 0. Only SessionStart, PreCompact,
and Stop hooks inject stdout context in this repo's convention.

### New hooks addition

All new hooks follow OUTPUT DISCIPLINE: stdout = pass-through JSON only, stderr = human text only.

| Hook | stdout tokens | stderr tokens | Default | Notes |
|---|---|---|---|---|
| harness-init SessionStart | ~15 (first ever) or 0 | 0 | ON | stdout is acceptable here — SessionStart stdout IS the context injection mechanism |
| pre-commit-gate (success) | 0 | 0 | ON | Silent |
| pre-commit-gate (advisory fail) | 0 | ~20 (1-line summary) | ON | Verifier output captured to temp file, NOT piped to stdout/stderr |
| post-test-analysis (success/non-test) | 0 | 0 | **OFF** | Silent |
| post-test-analysis (test fail) | 0 | ~25 (1-line summary) | **OFF** | Not enabled by default |
| **New total (defaults)** | | | | **~0-15 stdout, ~0-20 stderr** |

Note: stderr output from hooks does NOT enter Claude's context window. Only stdout is injected as context.
Therefore the real context impact of pre-commit-gate and post-test-analysis is **0 tokens** even on failure.
The only context-injecting new hook is harness-init SessionStart (~15 tokens, once per repo).

### Scenario analysis (defaults ON, /init-harness applied, post-test-analysis OFF)

| Scenario | Description | New stdout context | Existing stdout context | Total stdout context |
|---|---|---|---|---|
| A: Normal dev | 5 edits, 3 tests (1 fail), 1 commit (repeat repo) | 0 | ~20-65 | ~20-65 |
| A (first visit) | Same but first time in repo | ~15 | ~20-65 | ~35-80 |
| B: TDD heavy | 10 tests (7 fail), no commits | 0 | ~0-45 | ~0-45 |
| C: Quick fix | 1 edit, 1 test (pass), 1 commit | 0 | ~0-45 | ~0-45 |

Note: Existing stdout context comes from SessionStart (~0-45) + PreCompact (~0-20, if triggered) + Stop (~0-20, end of session).
Most existing hooks write to stderr only, contributing 0 stdout context tokens.
Stop output occurs at session end and does not affect mid-session reasoning quality.

**Key change from v1**: post-test-analysis is OFF by default, so TDD-heavy scenarios add 0 new tokens. pre-commit-gate is silent on success.

### Project-level hooks (generated by /init-harness, NOT counted in global budget)

Project hooks (prettier, tsc) fire per Edit but their output goes to stderr only — no stdout context injection unless there is an error. This matches the existing prettier-hooks pattern.

## Risks and Mitigations

| Risk | Mitigation |
|------|-----------|
| /init-harness duplicates hooks on rerun | Manifest-based identity (`.harness-manifest.json` with `_id` + `command_hash`) |
| qa-reviewer drifts into code review | Evidence collected by orchestrator (not Generator). No diff in evidence. Enforced in /orchestrate |
| qa-reviewer guesses instead of grading | Executable verifiers with expected results. Verdicts must match verifier output vs expected |
| pre-commit-gate blocks legitimate commits | Advisory default. Strict only via explicit HARNESS_GATE_MODE=strict |
| post-test-analysis too noisy in TDD | Default OFF. Opt-in only |
| console-log-guard per-edit noise | Not generated by default. Available via /init-harness --with-console-guard |
| Test runner detection misses wrappers | Extended pattern list: pnpm, yarn, npm run test:*, just, make ci-test, cargo, go |
| Existing users lose prettier/console-log-guard | Migration message + /init-harness provides equivalent project-level hooks |
| /init-harness overwrites user settings | Manifest tracks managed hooks only. User-added hooks preserved. Diff shown before write |
